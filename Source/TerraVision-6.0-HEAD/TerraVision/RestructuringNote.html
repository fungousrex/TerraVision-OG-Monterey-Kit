Notes On The Partitioning Of GUI and "Core" Functionalities in TerraVision



11/11/99



Background

As TerraVision was originally developed, its core functionality was tightly integrated with the Motif-based user interface. While this was suitable for the initial development, it later became apparent a cleaner separation of functions was needed to accommodate further development plans, such as a truly portable GUI and a browser-based plugin. Work is underway towards that goal, having begun in the summer of 1999. This document is a progress summary. To help focus future effort, an enumeration also is given of those functions that make up the interface to the application's "core" features.

The Approach to Partitioning

The overall strategy can by summarized as a physical partitioning of the code. Previously there existed structures that contained variables related solely to the Motif GUI, along with variables required by the intrinsic application features - the so-called "core" functionality. All the C-functions that operated upon these structs were typically lumped into one source code module, regardless of the specific role they served.



The program's core features were identified as the querying and rendering of the multi-resolution heirarchical databases. Codes related to the GUI were obviously anything that directly employed the Motif or X11 APIs. (There is another layer that serves as a sort of "middleware", providing features on top of the core capabilities. For purposes here, these will be discussed as core functions). All data related to core features was removed from the existing structs, placed into new ones, in new source code modules along with the functions that operate directly on them.



The largest instance of this was the ThreeDWidget struct. This was a rather large struct that contained most of the Motif widgets employed for the major application windows, plus much of the state data associated with the core functionality. A new struct named ThreeDCore was created, and all core data and functions were moved into new source code files. In the process, several variables contained in the structs ThreeDPanel and ThreeDControl were also removed and placed into ThreeDCore. The original ThreeDWidget struct contained a sub-structure named SharedWidgetInfo, which was deemed obsolete in purpose. This substruct was eliminated, with its variables dispersed into ThreeDWidget or ThreeDCore as appropriate. The net result is a series of source code files that contain most of the GUI codes associated with the main window and the "3D View" window:

ThreeDWidget.h

ThreeDWidgetI.h

ThreeDWidget.c

and a set of files that contain the core features of rendering and querying the databases, broken up roughly by subfunction to make the source files more manageable in size:

ThreeDCore.h

ThreeDCoreI.h

ThreeDCore.c // ctor, dtor, miscellaneous codes

ThreeDDraw.c // codes primarly for rendering database tiles

ThreeDVis.c // codes for visibility tests/calculations.

ThreeDNav.c // codes for view navigation and management



Similar partitioning was performed for codes related to the "Paths" functionality:

Paths.*: // the core "Paths" functions

PathsFE.* // the GUI codes related to "Paths"



for the "Features" functionality:

Features.*: // core "Features" functions and data

FeaturesFE.*: // GUI codes related to "Features"

and for network logging:

NetLogCore.* // core data and functions for logging

NetLogger.* // GUI codes for logging



Future Work

At this point, there is a reasonably clean separation of codes for the Motif GUI and those for the core TerraVision functions. While the GUI necessarily is dependent upon core functions to effect program behavior, there is little or no backwards dependencies of core features upon the GUI codes.



At present, the variables inside the core structs are visible to the GUI codes, and often are manipulated directly. Future efforts will be to design and create a set of "external" interfaces for the core features, through which any setting or querying of core state by outside agents (such as a GUI) may be performed. This object-oriented approach would expose only minimal details of the core features, and hide all of the internal workings from clients of the code codes.
